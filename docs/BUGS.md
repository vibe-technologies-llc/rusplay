# Video decode
- [S] `decode-vaapi-driver-field-long-term`: the VCN firmware behind Mesa's VAAPI H.264 decode (checked on Mesa 26.2.5, RX 9070) mis-marks a long-term field, with no client-side workaround. When a top reference field carries MMCO 2 for a long-term field of its own parity and directly follows a non-reference bottom field with the same `frame_num` (the end of a non-reference frame), the firmware unmarks the bottom field instead, presumably pairing the two fields; bottom-first non-reference frames and an earlier non-reference frame decode correctly. Mesa passes the DPB through faithfully: `vlVaHandlePictureParameterBufferH264` (`frontends/va/picture_h264.c`) turns each `ReferenceFrames` entry into `frame_num_list`, `is_long_term`, `top_is_reference`/`bottom_is_reference` and `field_order_cnt_list` (`INT_MAX` for an unmarked field) and ignores the slice's `RefPicList0/1`, `si_dec_h264` (`drivers/radeonsi/mm/si_video_dec.c`) maps entries to `render_pic_list` slots (`ref_frame_id_list`, `used_for_reference_flags` per field, `decoded_pic_idx` the first free slot, which is the one the non-reference picture just freed) and `build_avc_msg` (`amd/common/ac_vcn_dec.c`) sets bit 7 of `ref_frame_list` for long-term entries. The firmware keeps its own marking from the parsed `dec_ref_pic_marking` and per-slot picture state, and builds the lists itself: given the spec DPB it conceals the next P field with entry 0 throughout; given a DPB matching its own marking it decodes but references the wrong field; recreating the context loses every earlier reference. The ignored test `field_marking_unmarks_a_long_term_field_after_a_non_reference_frame` reproduces it; report it upstream (Mesa/AMD firmware) and re-run that test on newer firmware
- [S] `decode-rav1d-cdef-overlap`: rav1d 1.1.0 (the latest release; upstream main as of 2026-10 still has the code, there is no upstream issue or fix, and the `re_rav1d`, `hiraku-rav1d` and `rav1d-safe` forks carry none either) with many worker threads trips its `DisjointMut` overlap check in a debug build, but it is a false positive in the check, not a data race, so release builds read correct data. The panic is a `cdef.rs:207` read of the `top` line backup (`padding` takes a `(top.offset.., ..x_end)` window that starts 2 samples left of the block) overlapping the `&mut` write of `backup2lines` at `cdef_apply.rs:56` on another thread: the first block of a row (`bx == 0`, no `HAVE_LEFT`) never uses those 2 leading samples (`x_start` is 2 and the loop skips them) but the guard still covers them, and they are the last 2 samples of the previous line in `cdef_line_buf`, which for the first line of a superblock row belongs to the previous superblock row, whose CDEF task runs concurrently (a CDEF task waits only for `copy_lpf` of the row above, not for its CDEF). Every sample CDEF consumes comes from the task's own region (`cdef_line_buf + sby * 4 * stride`, written earlier by the same thread) or from read-only `lr_line_buf`/`cdef_lpf_line` data. It reproduces on radeonsi AV1 output (the 402x226 `sizes_off_the_block_grid_are_cropped` stream with 16 workers fails in 7 of 40 runs and in 0 of 60 with 2 or 4 workers) and not on the libaom fixtures. Slicing the guard from `x_start` (`(top.offset + x_start.., ..x_end - x_start)` indexed with `x - x_start`, and the same for `bottom`) in a local copy of 1.1.0 took it to 0 failures in 120 runs with 16 workers; the encode tests decode with one thread until a rav1d release carries that change

# Networking
- [S] `net-accept-origin-binding`: `accept` binds the session to whichever address sent the final `Confirm`/`Proof` (`rusplay-host/src/accept.rs:146`, `:181`; `pair_as_host`/`reconnect_as_host` in `rusplay-net/src/pairing.rs:621-628` and `reconnect.rs:485-491` do the same), and the responders never see `from`. A LAN observer can replay the unsealed final message from its own address first, and the host installs the keys and streams to it: no plaintext leaks, but the genuine client is locked out until it reconnects. `SessionTakeover` already records the `Hello` origin per attempt and honours `Proof` only from it (`takeover.rs:36-46`); do the same for `Start`/`Hello` in `accept` and both host drivers
- [S] `net-pairing-confirm-keeps-attempt`: a wrong `Confirm` for the active attempt clears it (`rusplay-net/src/pairing.rs:522-525`), and the attempt id travels in clear in `Start`, so one forged datagram kills the genuine pairing in flight after its budget slot was spent. `networking.md` gives reconnect the opposite rule (an attempt survives a bad `Proof`, `reconnect.rs:389-391`). Answer `WrongPin` but keep the attempt until it times out, and treat a `Rejected` from the host address as advisory on the client (`pairing.rs:299-302`, `reconnect.rs:193-196`) or document why not
- [M] `net-reconnect-attempt-eviction`: `ReconnectResponder` keeps 16 attempts and `SessionTakeover` 16 origins, both evicting the oldest on every fresh `Hello` for a known peer (`rusplay-net/src/reconnect.rs:344-346`, `takeover.rs:51-59`), and the `PeerId` is cleartext in every `Hello` (`rusplay-protocol/src/reconnect.rs:120-122`). Sixteen spoofed `Hello`s push the genuine attempt out and its `Proof` is ignored, which blocks reconnect and roaming takeover; the static id also lets a passive observer track a device. Evict answered or aged attempts before live ones or rate-limit per source; optionally replace the cleartext id with a per-attempt blinded one (HMAC of the client nonce under the secret)
- [S] `net-reassembly-fragment-cap`: `ReassemblyLimits` hard-codes `max_fragments: 8192` and `max_pending_frames: 8` (`rusplay-net/src/reassembly.rs:15-31`; `From<&NetworkConfig>` sets only the timeout) while the `Packetizer` sends up to 65535 fragments (`packetizer.rs:44-63`), so a keyframe above about 11.8 MB at MTU 1500 (4.2 MB at 576) is rejected packet by packet, and the keyframe the client then requests is just as large: the stream stalls with no error. Move both limits into `network` config and have the `Packetizer` return `FrameTooLarge` above the same cap
- [S] `net-discovery-nonce-and-name`: `fresh_nonce` is `subsec_nanos ^ port.rotate_left(16)` (`rusplay-net/src/discovery.rs:235-242`) where `networking.md` promises a random nonce, and `read_announce` accepts any UTF-8 name (`rusplay-protocol/src/discovery.rs:107-109`) while `ClientName` and `PeerRecord` reject control characters, so any LAN host can put control or bidi characters in the host list. Draw the nonce with `fill_random` and reject control characters in announce names
- [S] `net-peer-store-hardening`: `DirBuilder::mode(0o700)` only applies to a directory it creates (`rusplay-net/src/peers.rs:288-296`), so an existing 0755 `rusplay/` state directory stays as it is, and `load` neither checks the store file's mode and owner nor zeroizes the text holding the hex secrets (`:271-274`). `networking.md` says the directory is `0700` and key material is zeroized. Tighten an owned directory, warn on a group- or world-readable store and zeroize on load
- [S] `protocol-stream-description-bounds`: `StreamDescription::read` accepts a zero or 4-billion resolution, zero `reference_white_nits`/`peak_nits` and mastering min above max (`rusplay-protocol/src/stream.rs:115,130-145`), though the config rejects the inverted pair; `rusplay-scale/src/color.rs:112` divides peak by white. `networking.md` says decoding validates everything it reads. Only a paired host can send these, so this is robustness against a buggy host: add a `ProtocolError` variant per bound

# Host
- [S] `host-join-stops-first`: `HostStream::join` (`rusplay-host/src/session.rs:313-324`) joins stages in spawn order, control first, and calls `shared.stop()` only after each join returns; `wait` never stops first, and each stage sets the stop flag only on a normal return (`encode.rs:43-53`, `capture.rs:245-250`, `send.rs:310-315`). A panic in encode, capture or send in an unwinding build (dev, `profiling`) leaves control sending keepalives, so the client never times out and `rusplay-hostd`'s `wait_logging` blocks forever on a session with no video. Stop before joining and wrap each stage body in a guard that stops on unwind
- [S] `host-forced-keyframe-lost`: the encode stage clears `force_keyframe` (`rusplay-host/src/encode.rs:146`) before checking that the pipeline produced a frame, and `encode` returns `Ok(None)` after a DMA-BUF import fails over to shared memory (`pipeline.rs:272-279`) and `repeat` with no input yet (`:615-618`). The takeover keyframe from `Shared::suspend`, the one forced after a full send queue drops a frame, and a client request can all vanish; the internal two have no retry, so the client sees P-frames referencing a frame it never got. Clear the flag only once a frame reached the send queue
- [S] `host-takeover-input-reset`: on a session takeover the input stage only resets its `InputSequence` (`rusplay-host/src/input.rs:226-232`): the old client's held keys, buttons, touches and virtual pads stay until the new client's first snapshot (forever with `snapshot_interval_ms = 0`). `follow_client` also runs only for the first datagram of a drain (`:210-214`), so old-client datagrams applied after the reset raise `last` and the new client's input is dropped as `Stale`. Call `release_all` and reset `held` on an epoch change, and tag forwarded datagrams with the epoch so old ones are dropped
- [S] `host-takeover-microphone-reset`: the microphone stage keeps one `Reassembler` and one `ConcealingPlayer` for the session and never reads `shared.client.epoch()` (`rusplay-host/src/microphone.rs:54-90`), while a new client numbers packets from 0 (`rusplay-client/src/microphone.rs:82`), so after a takeover every packet is stale or late until the numbers pass the old session's (an hour-long session means about an hour of silence). Reset both on an epoch change, test it in `src/tests/media.rs`, and correct `host.md`'s "the host has no `Reassembler` of its own to reset"
- [S] `host-input-channel-bounded`: control forwards input datagrams over an unbounded `mpsc::channel` (`rusplay-host/src/session.rs:164`, `control.rs:344-351`), and each event is a blocking round trip to the injector thread with no timeout (`input.rs:97-103`). A stalled compositor makes input queue without limit and replay late as a burst, and a blocked injector keeps the stage from seeing the stop flag. Use a bounded `sync_channel` with `try_send` and a drop counter like the microphone path, and time out `RemoteTarget::call`
- [M] `host-gpu-fence-wait-unbounded`: with the default GPU fence wait, an unsignalled producer fence becomes a queue wait semaphore with no timeout (`rusplay-host/src/pipeline.rs:384-386`), and the encode thread then blocks on `PollType::Wait { timeout: None }` (`:512-518`, `:566-569`), so a producer whose fence never signals wedges the session and the join. `host.md` says such a producer still streams, which holds only for the CPU fallback. Bound the poll with a configured timeout ending the session (or dropping to the CPU wait), and correct `host.md`
- [S] `host-takeover-refresh-ignored`: the takeover path ignores a failed peer-store refresh (`rusplay-host/src/control.rs:230`, `.ok()`) where `accept` propagates it, so with an unreadable store a client removed by `peers forget` can still take over the running session from the in-memory list. `hostd.md` says a failed refresh never silently keeps the old list. Refuse the takeover when the refresh fails
- [M] `host-fallback-sticky-and-silent`: any DMA-BUF import error, including transient ones such as importer creation or `gate_on_writes` syscalls, requests the shared-memory fallback (`rusplay-host/src/pipeline.rs:272-279`), which turns `prefer_dmabuf` off for the life of the stream (`rusplay-capture/src/pipewire/mod.rs:359-367`); a failed hand-off is discarded and the same encoder retries on the readback (`pipeline.rs:463-464`, `541-547`). Neither shows in `HostStats`, so one hiccup costs 2-3x per frame until restart with no signal. Fall back only on format or modifier rejection, add `dmabuf_fallback`/`handoff_off` stats printed by hostd, and reopen the encoder after a failed hand-off
- [S] `host-rumble-after-libei-failure`: the input target's `service` returns on `self.desktop.service()?` before `self.gamepads.poll_rumble` (`rusplay-host/src/portal.rs:52-55`), and libei's `pump` keeps reading a closed socket (`rusplay-input/src/libei/injector.rs:240-247`). Once the compositor drops EIS, pads still inject but their uinput fds are never drained, so a game's `EVIOCSFF` upload blocks 30 s each time. Always poll rumble and return the first error, and skip the read once closed
