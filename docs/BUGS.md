# Video decode
- [S] `decode-vaapi-driver-field-long-term`: the VCN firmware behind Mesa's VAAPI H.264 decode (checked on Mesa 26.2.5, RX 9070) mis-marks a long-term field, with no client-side workaround. When a top reference field carries MMCO 2 for a long-term field of its own parity and directly follows a non-reference bottom field with the same `frame_num` (the end of a non-reference frame), the firmware unmarks the bottom field instead, presumably pairing the two fields; bottom-first non-reference frames and an earlier non-reference frame decode correctly. Mesa passes the DPB through faithfully: `vlVaHandlePictureParameterBufferH264` (`frontends/va/picture_h264.c`) turns each `ReferenceFrames` entry into `frame_num_list`, `is_long_term`, `top_is_reference`/`bottom_is_reference` and `field_order_cnt_list` (`INT_MAX` for an unmarked field) and ignores the slice's `RefPicList0/1`, `si_dec_h264` (`drivers/radeonsi/mm/si_video_dec.c`) maps entries to `render_pic_list` slots (`ref_frame_id_list`, `used_for_reference_flags` per field, `decoded_pic_idx` the first free slot, which is the one the non-reference picture just freed) and `build_avc_msg` (`amd/common/ac_vcn_dec.c`) sets bit 7 of `ref_frame_list` for long-term entries. The firmware keeps its own marking from the parsed `dec_ref_pic_marking` and per-slot picture state, and builds the lists itself: given the spec DPB it conceals the next P field with entry 0 throughout; given a DPB matching its own marking it decodes but references the wrong field; recreating the context loses every earlier reference. The ignored test `field_marking_unmarks_a_long_term_field_after_a_non_reference_frame` reproduces it; report it upstream (Mesa/AMD firmware) and re-run that test on newer firmware
- [S] `decode-rav1d-cdef-overlap`: rav1d 1.1.0 (the latest release; upstream main as of 2026-10 still has the code, there is no upstream issue or fix, and the `re_rav1d`, `hiraku-rav1d` and `rav1d-safe` forks carry none either) with many worker threads trips its `DisjointMut` overlap check in a debug build, but it is a false positive in the check, not a data race, so release builds read correct data. The panic is a `cdef.rs:207` read of the `top` line backup (`padding` takes a `(top.offset.., ..x_end)` window that starts 2 samples left of the block) overlapping the `&mut` write of `backup2lines` at `cdef_apply.rs:56` on another thread: the first block of a row (`bx == 0`, no `HAVE_LEFT`) never uses those 2 leading samples (`x_start` is 2 and the loop skips them) but the guard still covers them, and they are the last 2 samples of the previous line in `cdef_line_buf`, which for the first line of a superblock row belongs to the previous superblock row, whose CDEF task runs concurrently (a CDEF task waits only for `copy_lpf` of the row above, not for its CDEF). Every sample CDEF consumes comes from the task's own region (`cdef_line_buf + sby * 4 * stride`, written earlier by the same thread) or from read-only `lr_line_buf`/`cdef_lpf_line` data. It reproduces on radeonsi AV1 output (the 402x226 `sizes_off_the_block_grid_are_cropped` stream with 16 workers fails in 7 of 40 runs and in 0 of 60 with 2 or 4 workers) and not on the libaom fixtures. Slicing the guard from `x_start` (`(top.offset + x_start.., ..x_end - x_start)` indexed with `x - x_start`, and the same for `bottom`) in a local copy of 1.1.0 took it to 0 failures in 120 runs with 16 workers; the encode tests decode with one thread until a rav1d release carries that change
- [M] `decode-rav1d-error-path-panic`: rav1d 1.1.0 `rav1d_submit_frame::on_error` unwraps the frame header that `rav1d_decode_frame_exit` already cleared, so a frame that fails while its tiles decode panics inside `dav1d_send_data`, and release builds abort. The tile layout and tile sizes are now validated before rav1d sees a packet (`src/av1/`), so what remains are errors only the tile decoder can see: a symbol decoder overread (tile data too short for its blocks), a 4:2:2 partition the format forbids, and an intra block copy vector into the current superblock. `cargo +nightly fuzz run -O decode_software` in `fuzz/` still finds them within minutes. Fixing it needs a patched rav1d (`on_error` must not unwrap the cleared header)
- [S] `decode-rav1d-picture-unref-leak`: rav1d 1.1.0 `dav1d_picture_unref` replaces the picture with `Rav1dPicture::default()` and writes it back as a C struct, which holds one raw `Arc` (the empty `itut_t35` list, 48 bytes) that nothing releases, so every decoded picture leaks it. `fuzz/` runs `decode_software` with `ASAN_OPTIONS=detect_leaks=0` because of it
