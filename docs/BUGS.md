# Video decode
- [S] `decode-vaapi-driver-field-long-term`: after a field of a long-term frame is unmarked with MMCO 2 and a non-reference frame was decoded earlier, Mesa's VAAPI H.264 decode makes every macroblock of the next P field use reference entry 0 (software decode and the DPB state agree on the right lists, and ffmpeg's VAAPI path reproduces it); find a workaround or confirm a driver fix
- [S] `decode-rav1d-render-size`: `Rav1dDecoder` reports the coded frame size instead of the AV1 render size, so a stream whose encoder pads the frame decodes wider than it was captured (radeonsi codes a 402-wide AV1 frame as 408 and signals 402 as the render size; the VAAPI decoder already honours it)
- [S] `decode-rav1d-cdef-overlap`: rav1d 1.1.0 with several threads trips its `DisjointMut` overlap check between `cdef.rs:207` and `cdef_apply.rs:76` on radeonsi AV1 output (about one decode in eight of the 400x216 VAAPI test stream), which aborts a debug build; the encode tests decode with one thread until it is understood or fixed upstream

# Client
- [S] `client-loopback-test-timing`: the `tests/loopback.rs` tests that need a GPU adapter fail intermittently on a loaded machine (load average above 30), on master as well: while the decode thread is still warming up the 16-frame decode queue overflows (`frames_dropped`, extra `RequestKeyframe`s) and the latest-wins slot supersedes the opening keyframe before the present stage takes it, so assertions such as "first presented frame is a keyframe", "no keyframe requests" and the FEC-recovery counts race the decoder; make the host wait for the client to drain, or assert on what is invariant
- [S] `cursor-shape-loss`: a lost `CursorMessage` that carried the image leaves the client on the previous shape until the shape next changes, since position-only messages omit the image and the receiver has no way to ask for it again; the host should repeat the image periodically or the control channel needs a resend request
