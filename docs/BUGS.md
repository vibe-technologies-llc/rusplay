# Video decode
- [M] `decode-vaapi-import-motion-corruption`: an AMD client shows tearing-like colourful artifacts during motion on HEVC from the VAAPI encoder, and `video.decoder.copy_output = true` clears them, so the decoded pixels are right and the fault is between the VAAPI surface and Vulkan. Not reproduced on an RX 6900 XT with Mesa 26.2.6, where `tests/vaapi_pipeline.rs` reads 7680 frames clean. The affected client is a Radeon 890M on Mesa 26.2.6, and that test is clean there too, so synchronisation, surface reuse and the transfer copy out of the import are ruled out on it. A real session captured with `copy_output = false` (4480x1440 HEVC Main from an RX 9070 XT host) shows a bitstream fault instead: from POC 256 on, every long-term reference named a picture the decoder never had, because Mesa 26.2 narrows the encoder's `poc_lsb_lt` to 8 bits (`video-encode.md`), and `VaapiDecoder` submitted those pictures with an invalid reference and reported them good. Both are fixed (8-bit LSB on the encoder, `ReferenceMissing` on the decoder), and that alone produces motion-dependent corruption on any client. The `copy_output = true` observation could be the same fault, if the invalid reference resolves to different stale surfaces when the output is copied. Next: re-test the 890M against a host with the fix, with `copy_output = false`, and delete this item if it is clean; otherwise continue with the present stage comparison (`crates/rusplay-decode/tests/data/HEVC-MOTION.md`).
- [S] `decode-vaapi-driver-field-long-term`: the VCN firmware behind Mesa's VAAPI H.264 decode (checked on Mesa 26.2.5, RX 9070) mis-marks a long-term field, with no client-side workaround. When a top reference field carries MMCO 2 for a long-term field of its own parity and directly follows a non-reference bottom field with the same `frame_num` (the end of a non-reference frame), the firmware unmarks the bottom field instead, presumably pairing the two fields; bottom-first non-reference frames and an earlier non-reference frame decode correctly. Mesa passes the DPB through faithfully: `vlVaHandlePictureParameterBufferH264` (`frontends/va/picture_h264.c`) turns each `ReferenceFrames` entry into `frame_num_list`, `is_long_term`, `top_is_reference`/`bottom_is_reference` and `field_order_cnt_list` (`INT_MAX` for an unmarked field) and ignores the slice's `RefPicList0/1`, `si_dec_h264` (`drivers/radeonsi/mm/si_video_dec.c`) maps entries to `render_pic_list` slots (`ref_frame_id_list`, `used_for_reference_flags` per field, `decoded_pic_idx` the first free slot, which is the one the non-reference picture just freed) and `build_avc_msg` (`amd/common/ac_vcn_dec.c`) sets bit 7 of `ref_frame_list` for long-term entries. The firmware keeps its own marking from the parsed `dec_ref_pic_marking` and per-slot picture state, and builds the lists itself: given the spec DPB it conceals the next P field with entry 0 throughout; given a DPB matching its own marking it decodes but references the wrong field; recreating the context loses every earlier reference. The ignored test `field_marking_unmarks_a_long_term_field_after_a_non_reference_frame` reproduces it; report it upstream (Mesa/AMD firmware) and re-run that test on newer firmware
# Host
- [S] `config-bitrate-hint-max-unused`: `network.bitrate_hint_max_kbps` no longer does anything. The host clamps a `BitrateHint` to `network.bitrate_hint_min_kbps..=video.bitrate_kbps` (`HintPolicy::from_config`), because a maximum above the configured bitrate can never apply and one below it kept a cut stream from climbing back to the bitrate the host was configured for. The option is still parsed, validated against the minimum (`NetworkConfig::validate`, `bitrate_hint_range`) and shown on the Settings page as "Host hint maximum". Remove it from `rusplay-config` and the Settings schema, with a migration that drops the key so existing files keep loading
