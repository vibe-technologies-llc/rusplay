# Video decode
- [S] `decode-vaapi-driver-field-long-term`: the VCN firmware behind Mesa's VAAPI H.264 decode (checked on Mesa 26.2.5, RX 9070) mis-marks a long-term field, with no client-side workaround. When a top reference field carries MMCO 2 for a long-term field of its own parity and directly follows a non-reference bottom field with the same `frame_num` (the end of a non-reference frame), the firmware unmarks the bottom field instead, presumably pairing the two fields; bottom-first non-reference frames and an earlier non-reference frame decode correctly. Mesa passes the DPB through faithfully: `vlVaHandlePictureParameterBufferH264` (`frontends/va/picture_h264.c`) turns each `ReferenceFrames` entry into `frame_num_list`, `is_long_term`, `top_is_reference`/`bottom_is_reference` and `field_order_cnt_list` (`INT_MAX` for an unmarked field) and ignores the slice's `RefPicList0/1`, `si_dec_h264` (`drivers/radeonsi/mm/si_video_dec.c`) maps entries to `render_pic_list` slots (`ref_frame_id_list`, `used_for_reference_flags` per field, `decoded_pic_idx` the first free slot, which is the one the non-reference picture just freed) and `build_avc_msg` (`amd/common/ac_vcn_dec.c`) sets bit 7 of `ref_frame_list` for long-term entries. The firmware keeps its own marking from the parsed `dec_ref_pic_marking` and per-slot picture state, and builds the lists itself: given the spec DPB it conceals the next P field with entry 0 throughout; given a DPB matching its own marking it decodes but references the wrong field; recreating the context loses every earlier reference. The ignored test `field_marking_unmarks_a_long_term_field_after_a_non_reference_frame` reproduces it; report it upstream (Mesa/AMD firmware) and re-run that test on newer firmware
- [S] `decode-rav1d-cdef-overlap`: rav1d 1.1.0 (the latest release; upstream main as of 2026-10 still has the code, there is no upstream issue or fix, and the `re_rav1d`, `hiraku-rav1d` and `rav1d-safe` forks carry none either) with many worker threads trips its `DisjointMut` overlap check in a debug build, but it is a false positive in the check, not a data race, so release builds read correct data. The panic is a `cdef.rs:207` read of the `top` line backup (`padding` takes a `(top.offset.., ..x_end)` window that starts 2 samples left of the block) overlapping the `&mut` write of `backup2lines` at `cdef_apply.rs:56` on another thread: the first block of a row (`bx == 0`, no `HAVE_LEFT`) never uses those 2 leading samples (`x_start` is 2 and the loop skips them) but the guard still covers them, and they are the last 2 samples of the previous line in `cdef_line_buf`, which for the first line of a superblock row belongs to the previous superblock row, whose CDEF task runs concurrently (a CDEF task waits only for `copy_lpf` of the row above, not for its CDEF). Every sample CDEF consumes comes from the task's own region (`cdef_line_buf + sby * 4 * stride`, written earlier by the same thread) or from read-only `lr_line_buf`/`cdef_lpf_line` data. It reproduces on radeonsi AV1 output (the 402x226 `sizes_off_the_block_grid_are_cropped` stream with 16 workers fails in 7 of 40 runs and in 0 of 60 with 2 or 4 workers) and not on the libaom fixtures. Slicing the guard from `x_start` (`(top.offset + x_start.., ..x_end - x_start)` indexed with `x - x_start`, and the same for `bottom`) in a local copy of 1.1.0 took it to 0 failures in 120 runs with 16 workers; the encode tests decode with one thread until a rav1d release carries that change
- [S] `decode-av1-obu-framing-panic`: `cros-codecs` 0.0.6 `Parser::read_obu` panics on malformed OBU framing, and release builds abort on panic: `assert!(header.has_size_field)` in low-overhead mode (`codec/av1/parser.rs:1825`), `&data[start_offset..start_offset + obu_size]` with an unchecked LEB128 size (`:1876`) and `u32::try_from(obu_size).unwrap()` in Annex B mode (`:1846`). `rusplay-decode/src/vaapi/av1.rs:72` and `nvdec/color.rs:211` hand it packets straight from the network, so one truncated or crafted packet from the host kills the client. Walk the OBU header and LEB128 size in Rusplay first and return `Malformed { unit: Obu }` for a missing size field or a size past the packet end, with tests for both
- [S] `decode-h264-sps-size-panic`: `Sps::max_dpb_frames` in `cros-codecs` (`codec/h264/parser.rs:913-917`) divides by `width_mb * height_mb` in `u32`, and `parse_sps` bounds neither dimension, so an SPS of 65536x65536 macroblocks wraps the product to 0 and divides by zero. `rusplay-decode/src/vaapi/h264.rs:415` (`stream_format`) and `:368` call it unconditionally. Reject an SPS above level 6.2's 139264 macroblocks (or the driver's maximum picture size) with `ResolutionUnsupported` before the call, or compute the DPB size in Rusplay with checked arithmetic
- [S] `decode-visible-size-unclamped`: the VAAPI decoders report a display size the decoded surface may not have. AV1 takes `render_width`/`render_height` unclamped (`vaapi/av1.rs:278`) where the software path clamps to the coded size (`software.rs:126-131`) as `video-decode.md` requires; HEVC uses `sps.visible_rectangle()`, whose unvalidated conformance window wraps in `cros-codecs` (`codec/h265/parser.rs:999-1000`); H.264 and HEVC drop `visible.min` (`h264.rs:414`, `hevc.rs:645`), so a left or top crop is applied as a right or bottom one. The client sizes its textures from that resolution (`rusplay-client/src/present.rs:149`). Clamp to the coded size in `Stream::output_sized`, reject crop offsets beyond it as `Malformed`, and reject non-zero left/top offsets until the crop origin is carried
- [S] `decode-bitstream-arithmetic-overflow`: POC arithmetic on SPS and slice header values uses plain `+`/`*` (`vaapi/h264/dpb.rs:351,358,394,397`, `vaapi/hevc.rs:332,434,457`, where `cycle * max_lsb` can reach `i32::MAX` times 65536) and `h264.rs:435` adds 1 to a `u16` map-unit count, so crafted streams panic dev, test and fuzz builds and wrap silently in release. The same files already use `wrapping_*` elsewhere; use wrapping or checked arithmetic returning `Malformed` throughout

# Video encode
- [S] `encode-chroma-pitch-check`: `YuvFrame::from_frame` (`rusplay-encode/src/input.rs:105-123`) derives the chroma pitch as `ceil(luma_stride / 2)` and checks only the luma row and total length, so a 10/12-bit 4:2:0 or 4:2:2 frame with an odd width at minimum stride (401 wide, stride 802) gets a 401-byte chroma pitch for 402-byte rows, odd and misaligned for `u16` samples. The VAAPI upload's `sample()` (`vaapi/format.rs:100-102`) then indexes past the plane and panics, and x264/x265/SVT-AV1 get raw pointers that may over-read. The host's own upload rounds the width up to even (`rusplay-host/src/upload.rs:116`), so only other producers hit it today. Require `chroma_stride >= chroma_width * sample` and a stride divisible by the sample size, return `FrameStrideTooSmall` otherwise, and fix the contract sentence in `video-encode.md`
- [S] `encode-vaapi-hevc-poc-wrap`: investigate. The VAAPI HEVC encoder passes the POC LSB (`index % 65536`, `vaapi/hevc.rs:579`) as `pic_order_cnt` for the current picture and its references (`:498`, `:512`), where libva expects `PicOrderCntVal`; H.264 passes the unwrapped count (`vaapi/h264.rs:418`). With an infinite GOP the 65536th frame (about 18 minutes at 60 fps) has POC 0 against a reference at 65535 while the packed RPS says -1. A driver that derives delta POCs from the parameters (iHD writing its own slice header) would disagree with the bitstream until the next IDR. Pass the unwrapped index saturated to `i32` and keep only the LSB in the slice header; confirm with a long run on hardware

# Networking
- [S] `net-reassembly-pending-order-hang`: `Reassembler::insert_pending` keeps `pending` sorted with the wrapping `is_newer`, which is not a total order, so frame numbers spread across more than half the `u32` range can leave it unsorted, and `poll_timeouts` (`rusplay-net/src/reassembly.rs:154-171`) then spins forever, apparently because `drop_lost_through` only pops from the front and removes nothing when a newer, unexpired frame sits first. Found by the `reassembly` fuzz target within seconds (`fuzz/`); the receive stage of an authenticated peer hangs. Remove the expired frames by position, or reject frames too far from the floor, with a test
- [M] `net-reconnect-blinded-peer-id`: the `PeerId` is cleartext in every reconnect `Hello` (`rusplay-protocol/src/reconnect.rs`), so a passive observer can track a device, and a flood of `Hello`s from many spoofed source addresses can still fill the 64-entry attempt table of `ReconnectResponder` (shared by `SessionTakeover`) and evict the genuine attempt. Replace the id with a per-attempt blinded one (HMAC of the client nonce under the secret, tried against each store record) or make the host's challenge stateless; either changes the `Hello` encoding and bumps `ProtocolVersion::CURRENT`

# Host
- [S] `host-join-stops-first`: `HostStream::join` (`rusplay-host/src/session.rs:313-324`) joins stages in spawn order, control first, and calls `shared.stop()` only after each join returns; `wait` never stops first, and each stage sets the stop flag only on a normal return (`encode.rs:43-53`, `capture.rs:245-250`, `send.rs:310-315`). A panic in encode, capture or send in an unwinding build (dev, `profiling`) leaves control sending keepalives, so the client never times out and `rusplay-hostd`'s `wait_logging` blocks forever on a session with no video. Stop before joining and wrap each stage body in a guard that stops on unwind
- [S] `host-forced-keyframe-lost`: the encode stage clears `force_keyframe` (`rusplay-host/src/encode.rs:146`) before checking that the pipeline produced a frame, and `encode` returns `Ok(None)` after a DMA-BUF import fails over to shared memory (`pipeline.rs:272-279`) and `repeat` with no input yet (`:615-618`). The takeover keyframe from `Shared::suspend`, the one forced after a full send queue drops a frame, and a client request can all vanish; the internal two have no retry, so the client sees P-frames referencing a frame it never got. Clear the flag only once a frame reached the send queue
- [S] `host-takeover-input-reset`: on a session takeover the input stage only resets its `InputSequence` (`rusplay-host/src/input.rs:226-232`): the old client's held keys, buttons, touches and virtual pads stay until the new client's first snapshot (forever with `snapshot_interval_ms = 0`). `follow_client` also runs only for the first datagram of a drain (`:210-214`), so old-client datagrams applied after the reset raise `last` and the new client's input is dropped as `Stale`. Call `release_all` and reset `held` on an epoch change, and tag forwarded datagrams with the epoch so old ones are dropped
- [S] `host-takeover-microphone-reset`: the microphone stage keeps one `Reassembler` and one `ConcealingPlayer` for the session and never reads `shared.client.epoch()` (`rusplay-host/src/microphone.rs:54-90`), while a new client numbers packets from 0 (`rusplay-client/src/microphone.rs:82`), so after a takeover every packet is stale or late until the numbers pass the old session's (an hour-long session means about an hour of silence). Reset both on an epoch change, test it in `src/tests/media.rs`, and correct `host.md`'s "the host has no `Reassembler` of its own to reset"
- [S] `host-input-channel-bounded`: control forwards input datagrams over an unbounded `mpsc::channel` (`rusplay-host/src/session.rs:164`, `control.rs:344-351`), and each event is a blocking round trip to the injector thread with no timeout (`input.rs:97-103`). A stalled compositor makes input queue without limit and replay late as a burst, and a blocked injector keeps the stage from seeing the stop flag. Use a bounded `sync_channel` with `try_send` and a drop counter like the microphone path, and time out `RemoteTarget::call`
- [M] `host-gpu-fence-wait-unbounded`: with the default GPU fence wait, an unsignalled producer fence becomes a queue wait semaphore with no timeout (`rusplay-host/src/pipeline.rs:384-386`), and the encode thread then blocks on `PollType::Wait { timeout: None }` (`:512-518`, `:566-569`), so a producer whose fence never signals wedges the session and the join. `host.md` says such a producer still streams, which holds only for the CPU fallback. Bound the poll with a configured timeout ending the session (or dropping to the CPU wait), and correct `host.md`
- [S] `host-takeover-refresh-ignored`: the takeover path ignores a failed peer-store refresh (`rusplay-host/src/control.rs:230`, `.ok()`) where `accept` propagates it, so with an unreadable store a client removed by `peers forget` can still take over the running session from the in-memory list. `hostd.md` says a failed refresh never silently keeps the old list. Refuse the takeover when the refresh fails
- [M] `host-fallback-sticky-and-silent`: any DMA-BUF import error, including transient ones such as importer creation or `gate_on_writes` syscalls, requests the shared-memory fallback (`rusplay-host/src/pipeline.rs:272-279`), which turns `prefer_dmabuf` off for the life of the stream (`rusplay-capture/src/pipewire/mod.rs:359-367`); a failed hand-off is discarded and the same encoder retries on the readback (`pipeline.rs:463-464`, `541-547`). Neither shows in `HostStats`, so one hiccup costs 2-3x per frame until restart with no signal. Fall back only on format or modifier rejection, add `dmabuf_fallback`/`handoff_off` stats printed by hostd, and reopen the encoder after a failed hand-off
- [S] `host-rumble-after-libei-failure`: the input target's `service` returns on `self.desktop.service()?` before `self.gamepads.poll_rumble` (`rusplay-host/src/portal.rs:52-55`), and libei's `pump` keeps reading a closed socket (`rusplay-input/src/libei/injector.rs:240-247`). Once the compositor drops EIS, pads still inject but their uinput fds are never drained, so a game's `EVIOCSFF` upload blocks 30 s each time. Always poll rumble and return the first error, and skip the read once closed

# Client
- [S] `client-connect-hang-audio-failure`: when the audio stage fails at startup (an `open_decoder` error such as `AudioCodecNotCompiled` for FLAC without the feature, `rusplay-client/src/audio.rs:103-110`), `spawn_audio` stops and joins (`session.rs:494-497`) while `connect_stream` still holds the decode queue's sender (`:153-156`); present waits on the slot decode never closes and decode waits in `queue.recv()` (`decode.rs:83`), so `ClientSession::connect` never returns and the app sits on "Connecting" with the threads and authenticated transport leaked. - [S] `client-cursor-size-bounds`: `CursorUpdate::upload` creates a texture straight from a `u16` image size (`rusplay-client/src/window/cursor.rs:154-160`), the scaled size `image * target / space` uses a host-supplied `space` with no bound (`:64-66`, `232-235`), and `cursor.x - i32::from(image.hotspot_x)` is unchecked (`:71`, `:76`); the protocol checks only that the RGBA length matches (`rusplay-protocol/src/cursor.rs:127-133`). - [M] `client-static-relayout`: `set_layout` moves the subsurface at once (`rusplay-client/src/window.rs:315-327`), but the presenter skips frames not of `layout.pixels` (`:531-533`), updates the viewport only on a successful draw (`:604-608`), and the present stage drops each decoded frame after one submit (`present.rs:169-176`), so resizing, fullscreen or the header hiding on a static remote screen leaves the old-size picture at the new origin until the host sends a frame; a `None` layout keeps the last buffer mapped. Re-scale the last output on a target change (or request a keyframe), and unmap the subsurface when the layout is `None`
- [S] `app-pairing-secret-dropped`: if the user disconnects while a PIN connect runs, `connected` returns early (`rusplay-app/src/stream.rs:202-204`) and drops the `paired_secret` the host already stored; `remember_peer` matches the entry by address (`hosts/model.rs:188-201`), so a scan finishing mid-stream can make it return `false` with no notice. - [M] `app-custom-primaries-form`: `video.color.primaries`, `video.color.hdr.mastering.primaries` and `color.target.primaries` are `Kind::Choice(PRIMARIES)` with named sets only (`rusplay-app/src/settings/schema.rs:89-96`, `337`, `382`, `1298`), and `read_value` reads a choice with `as_str` (`form.rs:372-373`), so a `primaries.custom = { ... }` table reads as empty: saving any setting silently drops custom target or mastering primaries, and custom `video.color.primaries` blocks saving with "a value is required". `ui.md` requires every setting to be reachable; the coverage test's `populated_configs` uses named primaries only (`form.rs:569`, `578`). Add a primaries kind that keeps or edits a custom table and extend the coverage test with `ColorPrimaries::Custom`

# Colour
- [M] `color-tone-matrix-clip`: `ColorPlan` picks `MappingPath::Matrix` whenever the source gamut fits in the target, for perceptual, relative, desaturate and highlight alike (`rusplay-scale/src/color.rs:290-301`), even when a tone stage is active (`:309-321`). Tone mapping bounds only ICtCp intensity (`color_tone.wgsl:145-160`), so a saturated highlight keeps a channel far above the target peak (BT.2020 red at 400 cd/m² luminance has R near 1500), the matrix branch passes it unclamped (`color_gamut.wgsl:310-312`) and `compose.wgsl:79,92` clips it per channel, which shifts hue: BT.2020 PQ to a lower-peak BT.2020 display, BT.709 HDR to sRGB SDR. Use the perceptual path when a tone stage exists in perceptual mode (the boundary table already holds the upper faces), keep `is_identity` exact, and add a saturated BT.2020 PQ to 600 cd/m² BT.2020 test
- [S] `host-hdr-upscale-sigmoid`: the host's `scale_settings` turns sigmoid on whenever `scaling.upscale.sigmoid` is set (`rusplay-host/src/route.rs:116-129`), and upscaling forces the linear route where PQ/HLG run up to `peak / white`; `shape_input` clamps to 0..1 before the logit (`rusplay-scale/src/shaping.wgsl:19`, `sigmoid.rs:126`), so an HDR capture upscaled on the host has every highlight above reference white flattened before encoding. - [S] `color-h273-transfer-aliases`: `TransferFunction::from_h273_code` (`rusplay-core/src/color/transfer.rs:39-54`) maps only 1, 4, 8, 13, 16 and 18, so VUI transfer codes 6 (SMPTE 170M), 14 and 15 (BT.2020 10/12-bit, common from x265 and ffmpeg) read as unsignalled in `SignalledColor::with_h273_codes`.
