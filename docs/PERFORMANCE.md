# Video decode
- [M, blocked by: decode-nvdec-hardware] `decode-nvdec-zero-copy`: hand NVDEC pictures to the client as `DecodedBuffer::DmaBuf` instead of a host copy: copy the mapped surface device to device into a pooled exportable allocation (a DMA-BUF from `cuMemGetHandleForAddressRange`, or a VMM allocation exported as an opaque fd and imported with `VK_KHR_external_memory_fd`), described as linear `NV12`/`P010`/`NV16`/`P210`, so the client imports it like a VAAPI surface. Today every frame is mapped, copied to host memory with `cuMemcpy2D`, deinterleaved and shifted on the CPU and uploaded again by the present stage

# Host
- [S] `perf-virtual-first-frame-stale-size`: with `capture.source = "virtual"` on KWin the first frame is at the output's own 1920x1080 and the encoder opens and sends a keyframe at that size 80 ms to 0.5 s before the offered size arrives and a second keyframe follows (KWin 6.8.2, nested run in `.claude/rules/capture.md`). Hold the first encode until a frame of the offered size arrives or a short timeout passes, so the client never receives and decodes a keyframe it throws away
- [L, blocked by: encode-vaapi-rext-hardware] `perf-vaapi-packed-handoff`: VAAPI 4:2:2/4:4:4 always takes the readback because `ColorConverter` does not write the packed `YUYV`/`AYUV`/`Y410` family (`host.md`), so a 4K 10-bit 4:4:4 frame is still read back (49.8 MB, `GpuPipeline::encode_mapped` in `rusplay-host/src/pipeline.rs`) and packed on the CPU into the `VAImage` (`pack` in `rusplay-encode/src/vaapi/format.rs`, 3.0 ms at 4K 4:4:4 10-bit, 5.2 ms at 12-bit), serial with the encode, on a path `CLAUDE.md` calls first class. Write the packed layouts on the GPU and export them as a DMA-BUF through `Handoff::plan`, which removes the readback and the pack
