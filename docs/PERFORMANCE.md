# Video decode
- [M, blocked by: decode-nvdec-hardware] `decode-nvdec-zero-copy`: hand NVDEC pictures to the client as `DecodedBuffer::DmaBuf` instead of a host copy: copy the mapped surface device to device into a pooled exportable allocation (a DMA-BUF from `cuMemGetHandleForAddressRange`, or a VMM allocation exported as an opaque fd and imported with `VK_KHR_external_memory_fd`), described as linear `NV12`/`P010`/`NV16`/`P210`, so the client imports it like a VAAPI surface. Today every frame is mapped, copied to host memory with `cuMemcpy2D`, deinterleaved and shifted on the CPU and uploaded again by the present stage

# Networking
- [M] `perf-send-path-copies`: an encoded frame is still copied and allocated about four times before `sendmmsg`: VAAPI's coded buffer into a fresh `Vec` (`rusplay-encode/src/vaapi/va.rs:447-455`), AV1's temporal delimiter prepend (`obu.rs:18-20`), one `Vec` per datagram out of `Packetizer::packetize` (`rusplay-net/src/packetizer.rs`, `build_datagram`), and a sealed copy per datagram (`SessionCipher::seal`, `rusplay-net/src/session.rs`). The header prepend and the FEC shard copies are gone. Reserve header room in the encoder output, and have the packetizer write into a reused datagram arena that is sealed in place (`send_batch` would take slices of it instead of `&[Vec<u8>]`)
- [S] `perf-reassembly-assemble`: the client still memmoves the whole reassembled frame to drop the 8-byte `VideoFrameHeader` (`rusplay-client/src/receive.rs`, `data.drain(..VideoFrameHeader::SIZE)`) on the only thread draining the client socket. Carry the payload offset through `EncodedFrame` (`rusplay-core/src/media.rs`, 13 construction sites across the codec crates) or hand the decoder a slice, so no copy happens

# Host
- [M] `perf-shm-capture-copy`: every shared-memory capture frame is copied with `pixels.to_vec()` on the PipeWire thread (`rusplay-capture/src/pipewire/convert.rs:147`) before `write_texture` copies it again; at 4K `XR24` that is a fresh 33 MB mmap-backed allocation, about 8000 page faults, per frame, including frames the mailbox later supersedes. It is the path every failed DMA-BUF import falls back to. Hold the PipeWire buffer under a lease as the DMA-BUF path does (`pipewire/mod.rs:404-406`) so the upload reads mapped memory, or at least reuse a pooled buffer
- [L, blocked by: encode-vaapi-rext-hardware] `perf-vaapi-packed-handoff`: VAAPI 4:2:2/4:4:4 always takes the readback because `ColorConverter` does not write the packed `YUYV`/`AYUV`/`Y410` family (`host.md`), so a 4K 10-bit 4:4:4 frame is read back (49.8 MB, `rusplay-host/src/pipeline.rs:556-611`), repacked row by row (`upload.rs:133-158`) and packed per sample with bounds-checked `sample()`/`put_u16` (`rusplay-encode/src/vaapi/format.rs:112-190`, `vaapi/mod.rs:607-610`): about 180 MB of CPU traffic per frame, serial with the encode, on a path `CLAUDE.md` calls first class. Write the packed layouts on the GPU and export them as a DMA-BUF through `Handoff::plan`; meanwhile drop the repack copy and vectorise `pack` per row
- [M] `perf-thread-priority-client`: the client's receive, decode and present threads still run at default weight and default timer slack. Apply the same `network.frame_thread_nice` treatment to them (the host's encode, send and control threads already take it, `rusplay-host/src/priority.rs`), and add rtkit realtime scheduling over D-Bus as a fallback for an unprivileged user with no `RLIMIT_NICE` headroom

# Scaling
- [S] `perf-bind-group-cache`: the client makes a new output view every frame (`rusplay-client/src/present.rs:183`), so its last pass misses every frame and evicts nothing useful but still allocates a bind group per frame, which contradicts `scaling.md`'s nothing-allocated-per-frame contract. Cache the view beside each pooled output texture, and call `set_frame_capacity` on the scaler, converter and lineariser with the capture buffer count (up to 16 PipeWire buffers, `rusplay-capture/src/pipewire/format.rs:77-79`), since the default of 4 entries misses every frame above 4 buffers
