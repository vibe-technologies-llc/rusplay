# Video decode
- [M, blocked by: decode-nvdec-hardware] `decode-nvdec-zero-copy`: hand NVDEC pictures to the client as `DecodedBuffer::DmaBuf` instead of a host copy: copy the mapped surface device to device into a pooled exportable allocation (a DMA-BUF from `cuMemGetHandleForAddressRange`, or a VMM allocation exported as an opaque fd and imported with `VK_KHR_external_memory_fd`), described as linear `NV12`/`P010`/`NV16`/`P210`, so the client imports it like a VAAPI surface. Today every frame is mapped, copied to host memory with `cuMemcpy2D`, deinterleaved and shifted on the CPU and uploaded again by the present stage

# Host
- [L, blocked by: encode-vaapi-rext-hardware] `perf-vaapi-packed-handoff`: VAAPI 4:2:2/4:4:4 always takes the readback because `ColorConverter` does not write the packed `YUYV`/`AYUV`/`Y410` family (`host.md`), so a 4K 10-bit 4:4:4 frame is still read back (49.8 MB, `GpuPipeline::encode_mapped` in `rusplay-host/src/pipeline.rs`) and packed on the CPU into the `VAImage` (`pack` in `rusplay-encode/src/vaapi/format.rs`, 3.0 ms at 4K 4:4:4 10-bit, 5.2 ms at 12-bit), serial with the encode, on a path `CLAUDE.md` calls first class. Write the packed layouts on the GPU and export them as a DMA-BUF through `Handoff::plan`, which removes the readback and the pack
- [M] `host-gpu-queue-priority`: the convert and scale submission runs at the default Vulkan queue priority (`rusplay-scale/src/dmabuf/gpu_fence.rs` only adds extensions in the device-creation callback), so on a GPU-bound host it queues behind the game's own submissions while the encode thread waits in `poll_gpu` (`rusplay-host/src/pipeline.rs`), which is the up to 2x swing `host.md` already notes. Request `VK_KHR_global_priority` high for the device queue where the driver grants it (amdgpu may want `CAP_SYS_NICE` above normal, unchecked) and fall back on `NOT_PERMITTED`; measure with the ignored `handoff_frame_times` test beside an uncapped GPU load, both settings in one run
- [S] `capture-pipewire-rt-process`: the PipeWire stream connects without `RT_PROCESS`, so each buffer takes libpipewire's hop from the data loop to the main loop before `process` runs. Processing on the data loop removes one wake per frame but `HeldBuffers` is an `Rc<RefCell>` and `update_params` is called from `process`, so both need a thread-safe shape first

# Networking
- [S] `net-dscp-marking`: neither socket sets a DSCP or `SO_PRIORITY` (`Transport::bind` in `rusplay-net/src/transport.rs` sets only the buffer sizes), so on Wi-Fi the client's input and control datagrams share the best-effort queue with everything else. Add a `network` option, off by default, applied with `set_ip_tos`/`set_ipv6_tclass`, and measure input round trip on a busy Wi-Fi link with and without it before choosing a default; it does nothing on plain wired links
- [S] `net-parity-after-data`: `Packetizer::packetize_into` encodes every FEC block before the first datagram of the frame leaves, an estimated 0.05 to 0.2 ms on a P-frame and more on a keyframe. Send the data range first and encode parity while it is paced

# Input
- [M] `input-fewer-thread-hops`: an input event wakes five threads between capture and injection: capture thread to the client input stage's channel, the host control thread to the input stage's channel, and the input stage to the injector thread and back. Run the host's per-session input stage on the injector thread, fed directly by the control stage, and pack and send on the capturing thread on the client with the stage kept for timers, without losing the coalescing of motion that piles up behind a send

# Video encode
- [S] `encode-av1-screen-content`: the AV1 sequence header the VAAPI encoder writes has `seq_choose_screen_content_tools` off and `seq_force_screen_content_tools` 0 (`vaapi/av1.rs`, asserted in `vaapi/header_tests/av1.rs`), so palette mode and intra block copy are never offered to the VCN firmware on desktop text. Try `allow_screen_content_tools` on radeonsi (Mesa passes `palette_mode_enable` through), measure encode time and XPSNR on a text capture, and keep it only if it costs no latency

# Scaling
- [M] `scale-hdr-upscale-ringing`: for an HDR colour target the client turns the sigmoid off (`present.rs`, PQ and HLG light runs above 1) and `scaling.upscale.antiringing` defaults to 0, so an upscaled stream is resampled in plain linear light: a 1D Lanczos3 2x model of a 2 to 1000 cd/m² edge swings the dark side between -58 (clipped to black) and +32 cd/m². Add a PQ shaping stage beside the sigmoid in `rusplay-scale` (`shaping.wgsl`, `shaping.rs`, fused in the scaler like the sigmoid), which holds the dark side within 1.1 to 2.6 cd/m² in the same model but overshoots the bright side, so pair it with anti-ringing for that route; check on a live HDR compositor, which this path has not run on
